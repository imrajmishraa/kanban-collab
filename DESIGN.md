## Overview

This document describes the visual language of the Kanban Collab client: a dense, two-theme work surface for boards that several people edit at the same time. It follows the shape of the [Ant Design DESIGN.md](https://github.com/ant-design/ant-design/blob/master/DESIGN.md) — tokens first, in machine-readable front matter, then the reasoning behind them — because a token list without the rules that govern it is a palette, not a system.

The product is an operational tool, not a marketing site. A user lives in it for hours: columns of cards, a rail of boards, a panel of live activity, cursors moving in real time. That context sets the whole visual language. Every decision below favours density, calm and legibility over expressiveness, and the two themes are first-class — a team can switch mid-session without the interface losing its meaning.

Dark is the default and lives on `:root`; light overrides it under `.light`. There is no `.dark` block, so each token has exactly one definition per theme. `npm run lint:colors` fails the build if a component hardcodes a colour instead of asking for a token.

## Values

Four values generate the rest of this document. When a case is not covered below, resolve it with these.

**Quiet surfaces.** The page is the page. Black in dark, paper in light, and nothing in between that is decorative. A panel, a row, a chip or a bar is a surface or a wash — never a colour. Meaning travels in ink, not in fills, so a board's identity colour appears as text and a hairline edge rather than a coloured block. A screen full of tinted panels reads as noise; a screen of hairlines reads as structure.

**One accent, spent carefully.** Orange is the brand, and it is 2.72:1 on the light page, so it cannot carry text there. It therefore exists as a *fill* for identity discs and as `--brand` text only where the contrast allows — and in light the token swaps to a deep amber that can. The cream accent (`--accent`) is the one highlight that works on black; in light it becomes the same deep amber. Nothing else in the system is allowed to be a colour.

**Depth is a hairline.** No shadows on cards, panels, popovers or menus. Separation comes from a one-pixel warm edge (`--hairline`) and, at most, one step of lightness. A shadow on a black page reads as grime, and a stack of soft shadows reads as a mockup rather than an application.

**Small type, tight tracking.** Interface text runs 12.5–14px at 400–500 weight, headings 19–26px at 600–700 with negative tracking. Numbers, keycaps and micro-labels use the mono face at 9–10px, uppercase, widely tracked. This is a deliberate density choice: it fits a column of cards and a rail of boards on one screen without scrolling, which is the whole point of a board view.

## Colour

Two axes, and they never mix.

**Surfaces** are a ladder: `--bg-root` is the page and also every floating surface, then `--bg-surface`, `--bg-card`, `--bg-elevated` for panels that must lift. In dark the ladder climbs from pure black; in light the top three collapse to white and separation is carried entirely by hairlines. That is why no component may assume a background differs from its parent — the edge is the guarantee, not the fill.

**Washes** are white in dark and black in light, and they come in two strengths for two jobs. **Interaction** uses `--bg-hover` (10%) and `--bg-active` (15%) — deliberately louder than the scale, because a hover that has to be hunted for is not feedback. **Static** washes use the `--tint-N` scale (3% to 16%), where a component asks for a strength and the theme decides the direction: `--tint-4` is the workhorse at 303 call sites, `--tint-3` and `--tint-2` carry most of the rest. One class string works in both themes either way.

Two colours escape the system by design, and each has a written reason. The **hairline** is warm (`rgba(255,245,235,…)`) rather than neutral, so panels read as paper edges rather than as grid lines; it is not a brand colour, which is why it has its own token and its own value per theme. The **inverse** family exists for the tooltip, which flips: a light capsule on a dark page, a dark one on a light page, with `--inverse-accent` for the highlighted phrase so it does not vanish into the capsule.

Status colour (`--success`, `--warning`, `--danger`) is text and border only. A failed field is a `--danger` edge and a `--danger` message underneath — never a red-filled input.

## Typography

Plus Jakarta Sans carries the interface; JetBrains Mono is reserved for numbers, keys, timestamps and micro-labels where alignment matters. Both ship as dependencies (`@fontsource-variable/*`, imported in `main.tsx`) and are bound to `font-sans` and `font-mono` by the `@theme` block in `index.css` — so no font is fetched from a CDN, and a component that writes `font-mono` gets the mono face rather than the browser's default. Body copy never uses the mono face. Numeric columns get `tabular-nums` so a live counter does not shuffle sideways as it counts.

The scale is deliberately short — five UI sizes and one mono size. A screen that needs a sixth is usually a screen that needs fewer things on it. Headings are tight (`-0.01em` to `-0.02em`) because at 19–26px the default spacing looks loose beside 12.5px body text.

## Shape

Radius encodes what a thing is, not how big it is:

- Controls, rows, fields, cards: `rounded-lg` (8px).
- Panels, popovers, menus, toasts: `rounded-xl` (12px).
- Dialogs: `rounded-2xl` (16px).
- Avatars, dots, chips, segmented controls: full circle.
- Primary and secondary buttons: an asymmetric cut — `rounded-none rounded-tr-lg rounded-bl-lg`, mirrored for the outline variant. It is the one decorative gesture in the system, and it appears exactly twice.

## Motion

Motion answers a question or it does not ship. Colour, hover and focus transitions run 150ms on `ease`; layout shifts and widths 200ms on `ease-out`; menus and popovers 150–200ms as opacity plus a 2px translate. Nothing scales on entry — scaled text reads as a zoom bug.

Animate `transform`, `opacity`, `width`, `max-height` and `clip-path`. Never animate `box-shadow`. Every transition carries `motion-reduce:transition-none`, and the whole system degrades to instant under `prefers-reduced-motion`.

The one piece of choreography is the **theme reveal**: the class flip is wrapped in a View Transition and the snapshot is clipped to a circle centred on the control that was pressed. Going light, the new frame opens out of the button over 1200ms on `cubic-bezier(0.22, 1, 0.36, 1)`; going dark, the old frame closes back into it over 900ms on `cubic-bezier(0.6, 0, 0.4, 1)`. Both start and end at the button's own radius, so the two directions mirror each other. Two rules keep it honest: the origin is published as `--vt-x`, `--vt-y` and `--vt-seed` *before* the transition starts, so the incoming frame is already clipped on its first paint and the page never flashes whole; and a reveal that is still running is torn down rather than stacked, so a second press never leaves two irises fighting over the same snapshot. With no View Transitions support, or reduced motion, the theme changes with no animation at all.

## Motion principles

Ten principles of animation, each translated into what it may do in a dense work
surface. They are tools for the single rule above: **motion answers a question or
it does not ship.** A component picks at most two. None overrides reduced motion,
and none carries information that is not also in text, colour or position.

| # | Principle | Here it means | Limit |
|---|---|---|---|
| 1 | Squash & stretch | A press: `scale(0.97)` for 100ms on `:active`, back on release. Controls only. | Never on entry (the rule above stands), never on a text-bearing surface mid-layout. |
| 2 | Anticipation | A 2px lift and the hairline firming up the instant a card is picked up, before it moves. | ≤ 100ms. Only for drag, delete and other moves a person might regret. |
| 3 | Staging the focus | One thing moves; the rest holds still. The new card, the remote cursor, the dialog over a scrim. | One focal animation per region at a time. A second one waits or is dropped. |
| 4 | Pose to pose | Write two states, `data-state="open\|closed"`, and let CSS interpolate. | No JS-driven per-frame interpolation. No keyframes where a transition will do. |
| 5 | Follow through | A dropped card or an arriving toast settles on `ease-settle` and stops. | Overshoot ≤ 2px or 4%. Drop and arrival only. |
| 6 | Slow in, slow out | Entering: `ease-out`. Leaving: `ease-in`. Travelling across the screen: `ease-in-out`. | `linear` only for a progress rail or a spinner. |
| 7 | Arcs | A card sent to a column more than one away follows a curve (translate on x with an offset ease on y). | Everything else is a straight line. The theme reveal is already an arc. |
| 8 | Secondary action | A count ticking while a card lands; a dot appearing on the rail. | One supporting motion per primary one. It never delays the primary, and it is never the only signal. |
| 9 | Snappy timing | Feedback within 100ms of input; 150ms colour and hover; 200ms layout; 300ms is the ceiling. | Over 300ms needs a reason in the PR. The theme reveal (1200 / 900) is the only standing exception. |
| 10 | Exaggerated feedback | Make the *size* of a result larger, not its duration: a rejected field shakes ±4px for 240ms. A save confirms on the button itself. | Always paired with the `--danger` edge and message. Under reduced motion, only the edge and the message remain. |

Two consequences worth stating. **Squash & stretch does not contradict "nothing
scales on entry":** it is feedback to an action, and an entry is not one. And
**exaggeration is about amplitude, not length:** a longer animation reads as
slower software, a larger one reads as a clearer answer.

A component that cannot say which question its motion answers has none.

## Layout

A fixed rail on the left (256px, or 72px collapsed), a 56px navbar that blurs as content scrolls beneath it, and one scrolling content column. The rail is the page colour, separated by a hairline — it is not a panel. Below `md` the rail becomes a sheet and the navbar keeps the menu affordance; nothing else in the layout changes.

Content max-widths are per-route rather than global: a board is as wide as the viewport because columns are the unit of work, while settings and marketing pages cap at a reading width.

## Components

The recipes in the front matter are the contract. A few rules sit behind them.

**One solid button per screen.** The solid variant is the primary action and nothing else; beside it sits an outline, and everything else is ghost. A toolbar of three solid buttons has no primary action.

**Every icon-only control carries `aria-label` plus a tooltip with the same string.** The tooltip is not decoration; it is the label made visible.

**Floating surfaces are the page colour.** Popovers, menus and dialogs sit on `--bg-root` and are separated by a hairline. `--bg-elevated` exists but is not used for them: a grey panel on a black page reads as a different material rather than a layer.

**Toasts are the exception, and it is deliberate.** A toast arrives over content that is already in motion, so it has to read as a layer rather than as another page: `--bg-elevated` with five percent of the ink as a gradient across the top edge, and a hairline that is one step stronger than the card's. The gradient is what separates a panel from a slab at this size.

**Fields do not glow.** Focus firms the hairline from `--hairline` to `--hairline-strong` and nothing else — no orange halo, no ring. A label sits above at `text-sm font-medium`, a hint below at 11px muted, and an error replaces the hint in `--danger` with a `--danger` edge on the field.

**The active segment is the only filled control.** In a segmented control the selected option takes `--accent-fill` with `--accent` text — dark brown with cream, never orange.

**Chips keep their colour as text.** A label chip is a neutral `--tint-4` fill, a hairline edge, mono uppercase text. The card's identity colour is the text colour, not the background.

## Toasts

A toast is the one surface with variants, because it carries a different job
depending on why it appeared. The tables that back them live beside the
component in `toasterVariants.ts`; the two facts both halves of the toast need —
the surfaces and the lifetimes — live in `lib/toastTokens.ts`, because the call
(`lib/toast.ts`) and the surface (`components/toaster/`) may not import each
other.

**Seven axes, not twenty props.** `Toaster` takes `appearance`, `layout`,
`behaviour`, `a11y`, `classNames`, `preset` and `id`. Everything painted is in
`appearance`, everything measured in `layout`, everything timed in `behaviour`,
every label in `a11y`. A new attribute is a field inside a group, so the API
cannot creep back over the eight-prop cap in `docs/change-rules.md` §3.

**Presets** — `default`, `quiet` (one visible toast, a `soft` fill, no dismiss
button, the moment lifetime), `assertive` (five visible, expanded, 8s), `auth` (the auth
tone at `lg`), `compact` (320px, tighter gap and offset). A preset is merged
*under* the explicit groups, never over them: a preset that could override what
the caller wrote would be a transient mode in a persisted key with a nicer name.

**Shape** — seventeen, in three families, and it is the tooltip's set minus the
ones that paint a colour. **Radius**: `default` `{rounded.xl}` (the card radius),
`sharp` 4px, `soft` 16px, `pill` full, `card` 20px, `glass` 16px plus a blur —
only `glass` blurs. **Silhouette**: `speech` (one square foot, pointing),
`tab` (square foot, rounded head), `squircle`, `chamfer` (corners cut with a clip
path), `ticket` (notched edges), `blob`. **Edge**: `dashed`, `double` (a ring
offset from the border), `keycap` (a 3px bottom edge), `sticker` (2px, tilted a
degree), `callout` (a 3px left edge in the text's own colour). The two clip-path
shapes also clip the shadow, as they do on a tooltip. The shape is the only
writer of the radius: the surface table deliberately carries no
`--border-radius`, so the two cannot disagree.

What is *not* here is the tooltip's colour-bearing shapes — `neon`, `gradient`,
`ink`, `paper`, `blueprint`, `terminal`, `badge`, `solid`, `outline`. On a toast
those are `tone` and `fill`, and a second way to say the same thing is how a
surface ends up with two writers.

**Size** — five steps of the type scale inside the bubble, title over
description: `xs` 11/10px, `sm` 12/11px, `md` 13/12px (the default), `lg` 15/13px,
`xl` 17/14px. The description is `--toast-description` at every size, which a
filling tone overrides; a description that competes with the title is a
paragraph, and a toast is not a place for one.

**The description is its own slot.** `appearance.description` takes `size` (a
step of its own, `xs`–`lg`, so a `lg` title can carry an `xs` footnote), `color`
(any token or CSS colour, written to `--toast-description`) and `lines` (the
tooltip's `maxLines`, carried as `--toast-lines` so the clamp follows the number
rather than a fixed class — `1` is a single line, and anything not positive or
absent is natural height). `ink` does
the same for the title: an explicit `--normal-text` for a colour the tone table
does not have. Both go through variables, never a generated class, because a
class built from a runtime string is never compiled.

**Tone** — the surface, and there are eleven. `auto` is the elevated panel above;
`neutral` is the same panel without the gradient. `brand`, `success`, `warning`,
`danger` and `info` fill with their token — the last four are the tooltip's tone
table, `info` on `--link`, which the toast had been missing while `toastInfo`
painted a plain panel. `muted` is the surface a toast takes when it should
recede: `--bg-surface` with a hairline, the inks the tooltip's `outline` variant
uses. `auth` is the blue that belongs to neither the accent nor the status set:
it marks a moment rather than a result — signing in, finishing onboarding — so it
fills the whole toast and dismisses faster than a success does. `accent` is the
one place the accent is allowed to fill, in the segmented control's pair
(`--accent-fill` with `--accent` text): a single "look here" that is not an error.
`inverse` is the tooltip's family — a light capsule on a dark page, a dark one on
a light page — for a toast that has to sit *above* a busy board rather than
beside it.

**Fill** — how hard a tone is applied, three strengths, each one a recipe this
document already had for something else:

| Fill | Recipe | Where it comes from |
|---|---|---|
| `solid` | the tone fills the surface | `button-solid`, the status buttons |
| `soft` | the tone tints the panel and edges it; the ink stays the page's | `chip`, `brand-muted` + `brand-border`, `accent-soft` |
| `outline` | no fill; the tone is only the edge | `button-danger`, the tooltip's `outline` |

Ten tones at three strengths is thirty surfaces — `auto` has no colour to
soften, so it stays the gradient panel at every strength — and it is one table
plus one function (`toneSurface`) rather than thirty rows. `solid` is the
default, so a tone alone keeps the surface it always had. `soft` and `outline`
deliberately leave the text in the page's ink: colour is information here — it
edges the surface and backs the icon, it does not become the text.

**A filled tone carries three inks, not one.** The title takes `--normal-text`,
the description `--toast-description`, the close glyph `--toast-close`, and a
tone that fills the surface sets all three — otherwise the description keeps the
page's grey and disappears into the fill. The ink on a status fill is
`--inverse-text`, not white: the status tokens are bright in the dark theme and
dark in the light one, and white on `--success` is 1.9:1 where the ink that flips
with them is 10.3:1. `auth` is the exception — a blue that wants white in both
themes.

**Width has four numbers, and each has one home.** `width` is sonner's `--width`
(380px by default). `mobileWidth` is the cap below sonner's own 600px breakpoint,
where it stops reading `--width` and gives each toast
`calc(100% - 2 × mobileOffset)`; the cap travels as `--toast-mobile-width`
because a class built by interpolation is never generated at build time.
`maxWidth` is a cap on top of either, and `minWidth` is the floor below which the
content wraps rather than shrinks — the one of the four that stops a narrow toast
from breaking a long word across three lines.

**Lifetimes** — one table, in ms: a success is read at a glance (3s), an error
has to be read *and* acted on (6s), a moment is briefest (2.5s), and the stack's
default is 4s. A per-toast duration still wins, and a per-toast `delay` holds the
toast back — 200ms is how a save that usually finishes in 40 stops flashing a
toast at all.

**Motion** — its own group, because `enter` and `exit` are separate decisions: a
stack that fades in and slides out is a normal thing to want, and one property
for both is the compromise that makes it impossible. `animation` takes a
shorthand string (`"fade"`) or the group — `enter`, `exit`, `duration` in ms,
`easing` as any CSS timing function, and `respectReducedMotion` (default on),
which adds `motion-reduce:!transition-none`. The four properties are `scale`
(transform and opacity together, the default), `fade`, `slide` and `none`; when
enter and exit differ they become state-scoped classes on sonner's own
`data-mounted` and `data-removed`, which is the only place those two can diverge.

**Progress** — `progress.visible` draws a rail along one edge of the toast, from
`--toast-progress`, `--toast-progress-thickness` and `--toast-progress-duration`.
It is the toast's own `::after`: no extra element, nothing long content can push
out of the bubble, and no second timer — the rail reads the same `duration` the
dismissal does, so the two cannot drift. `animated: false` leaves a still
hairline instead, for a toast that is a label rather than a countdown, and
`showOnLoading: false` hides it on a loading toast — which has no lifetime to
count down — off sonner's own `data-type="loading"`.

**The dismiss button sits inside the bubble.** Sonner anchors it to the outside
corner by default, floating on the page; here it is a flex child, so it is
centred for any content height, and ordered last so it stays at the right edge.
24px, `{rounded.md}`, no fill, no border: the glyph is the affordance, and the
hover tint is the only feedback.

**The action buttons are 44px tall below `sm` and 28px above it.** A toast with
"Undo" on it is the one control a thumb reaches for in a hurry, and
`docs/change-rules.md` §5.1 sets the touch floor at 44×44. The desktop height is
what the design asks for; both are one control.

**Per toast, not per stack.** A `Toaster` prop reaches every toast; `lib/toast.ts`
reaches one. `tone` and `fill`, `descriptionTone` (a warning line inside a
neutral toast — the tooltip's attribute of the same name), `icon` (a glyph for
one toast), `copyValue` (a Copy button, ignored when an `action` is set), `id`
(re-fire replaces instead of stacking), `preventDuplicate` (derives that id from
the kind and the message, so a poll that fails every tick is one error),
`action` and `cancel`, `dismissible`,
`closeButton`, `onDismiss`, `onAutoClose`, `toasterId` and `testId` live there.
`id` is what turns "Saving…" into "Saved" in place rather than into two toasts,
and `toastPromise` is the same idea for a whole async operation.

**One import for callers.** `useToast()` returns all seven calls as one object —
`toast.success`, `toast.error`, `toast.promise` — so a component imports the
thing it uses rather than remembering which of seven names to bring in, and a
later line that needs `toast.warning` costs no import change. The object is
built once at module scope and its signatures are `typeof` the library's own
functions, so it cannot drift from them. `lib/toast.ts` stays the place a
service imports from, because `hooks/` is above it in the import matrix.

## Responsive

`docs/change-rules.md` §5 is the gate: what fails the build, and what a reviewer
checks. This is the design half — where a layout may change shape, and what it
becomes at each step.

**Mobile first.** Every layout is written as the narrow one and gains columns at
`sm:`, `md:`, `lg:`. A `lg:` rule with nothing between it and mobile is the shape
that squeezes at 768px, and the middle surface is the one nobody opens and the
one this repo has already shipped broken.

**Four breakpoints, not six.** Tailwind's defaults are the whole vocabulary: `sm`
640, `md` 768, `lg` 1024, `xl` 1280. A fifth value means the content broke
somewhere the scale did not cover — fix the content, or say in the PR why this
one needs a step of its own.

**The sweep.** 320, 375, 768, 1024, 1280, 1440, 1920, 2560. Between two widths
that both look right there is a width that does not, so also open the widths
where this app changes shape: 700, 720, 920, 1024, 1280, 1920 (`AGENTS.md` §6).
The usual suspects are 640 and 768, because a library, a layout and a grid each
pick their own switch — sonner stops reading `--width` at 600, Tailwind's `sm` is
640, and the board's columns move at a third point.

**Eight checks, in this order.** Horizontal overflow, text overflow, navigation
transition, stacking order, media scaling, touch targets, whitespace balance,
primary action above the fold. They are ordered by how often each is the actual
bug, and all eight vary with width — the rest of accessibility does not, and
belongs in the audit that does not resize.

**Touch is a size, not a style.** 44×44 is the floor, `h-11` / `size-11`. The
toast's action buttons are 44 below `sm` and 28 above it; the close glyph is 24,
and that is a known gap rather than a precedent. Nothing may be revealed by
hover alone.

**Type does not scale with the viewport.** `clamp()` belongs to marketing
headlines, where a 40px jump is a composition. The app's dense surfaces keep
fixed steps — 12 / 13 / 15 inside a toast — because a board column that reflows
its type is a column that jitters while you drag.

**Height is `dvh`.** `100vh` is wrong on iOS, where the browser chrome lives
inside the viewport; anything pinned to the bottom also carries
`env(safe-area-inset-bottom)`.

**What a breakpoint may change:** column count, whether the rail is a drawer or a
strip, whether a panel sits beside or below, how dense a list is. **What it may
not change:** what a control does, where the primary action is, or which
information exists. A narrow screen is a smaller viewport, not a smaller feature
set.

## Accessibility

Measured against the page they sit on, in each theme:

| Token | Dark on black | Light on 250 | Use |
|---|---|---|---|
| `--text-primary` | 19.3:1 | 16.7:1 | Body and headings |
| `--text-soft` | 13.3:1 | 11.2:1 | Secondary body |
| `--text-secondary` | 9.6:1 | 6.6:1 | Supporting text |
| `--text-muted` | 6.3:1 | **4.23:1** | Meta text only in light — see below |
| `--text-subtle` | 3.0:1 | 2.4:1 | Placeholders and disabled only |
| `--accent` | 17.0:1 | 6.8:1 | Highlight phrase |
| `--brand` | 7.4:1 | 2.7:1 | Never text in light; the token swaps to `#c2410c` at 4.96:1 |

One known gap, stated plainly rather than glossed: **`--text-muted` misses AA in light at 4.23:1**, having been lifted to a comfortable 6.3:1 in dark. It is therefore safe for timestamps, counts and labels beside a stronger element, and not safe for a sentence a user has to read. Closing it means `rgb(115)` in the light block — 4.54:1 — which is a token change, not a component change, and the only reason it is still open is that it shifts the light theme's quiet grey a shade darker everywhere at once.

Focus is visible on every interactive element through a global `:focus-visible` ring, except fields, which use the border change described above. Dialogs trap focus, close on Escape and on a backdrop press, and restore focus to the trigger. Live regions announce board changes; the activity feed is a `log`, not a list.

## Adding to the system

A new component is added by writing its recipe into the front matter of this file first, then the component. If a value cannot be expressed with an existing token, the answer is a new token in `index.css` with a value in both themes — not a colour literal in a `className`. `npm run lint:colors` enforces the last part; the rest is review.
